Job descriptions are written for humans, so they describe skills in whatever
words the hiring manager reached for that morning. Anything downstream —
matching, gap analysis, market data — needs the opposite: **canonical IDs, and
some sense of whether a skill is genuinely required or merely nice to have.**
Treating "5+ years of Postgres" and "familiarity with relational databases a
plus" as the same signal makes the whole system worse than useless.

## Two problems wearing one coat

The model has two heads.

The first is multi-label classification over the skill taxonomy — `UUID`
linking rather than free-text extraction. That distinction matters more than it
sounds: extracting the string "PyTorch" is easy, but deciding that it maps to
one specific taxonomy entry, and that "torch" in a different posting maps to the
same one, is the actual problem. The long tail of rare skills is where this gets
hard.

The second is an ordinal head for requirement strength. Required outranks
preferred outranks nice-to-have, and that ordering is real, so the loss should
know about it rather than treating the three as unrelated classes.

## Labels that did not exist yet

There was no labelled corpus for this, and hand-labelling at the required volume
was not realistic. So the labels were generated by an LLM and then verified by
humans — a teacher-student setup where the expensive model runs once, offline,
and the cheap model does the work that has to run at scale.
